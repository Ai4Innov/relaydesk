# Reviewed Google Calendar browser moves

Relay Desk can apply a **confirmed reschedule** through its paired Edge/Chrome
companion. This uses the signed-in Calendar page's visible controls, not Google
OAuth, Calendar APIs, cookies, private endpoints, injected arbitrary JavaScript,
or shell commands.

## Using it

1. Reload the updated unpacked companion in Edge/Chrome, then reload Calendar.
   Existing pairing credentials remain valid.
2. Select the browser Calendar account/source in Relay Desk. Keep its Calendar
   tab visible, with the exact captured event visible in Schedule/Agenda.
3. Ask chat to move the meeting. Review the exact account, meeting, previous
   displayed time, new date, start/end times, and **IANA time zone**
   (for example `Europe/Paris`). An implicit computer-clock zone is insufficient.
4. Confirm the proposal in Relay Desk. Leave Calendar untouched while the
   companion stages the fields and verifies the save.

Google's ordinary guest-update behavior applies. **Notifications may be sent**.
If Google asks whether to send updates or requests another confirmation, Relay
Desk stops and asks you to finish in the browser; it does not choose silently.

## Supported boundary

The first implementation supports one non-recurring, timed event, ending later
on the same date. The event must be uniquely located by its captured provider
identifier, not merely by its title. English/French accessible editor controls
and unambiguous locale dates are supported. Calendar must prove the event's
zone through labelled controls or its time-zone picker: either an IANA value
or one of the exact, geographically explicit selected labels listed below.
Numeric UTC offsets alone and unrecognized or ambiguous display names are
**not** treated as proof of an IANA zone.

The date/time controls also recognize the native IDs observed in a read-only
live editor inspection: `xTiIn`, `xStDaIn`, `xStTiIn`, `xEnDaIn`, `xEnTiIn`, and the
header Save button `xSaveBu`. Inspection did not modify or save the live event.
The observed English `23 Sept 2026` date and `3:00pm` time shapes are preserved
when staging changes. The picker is read through the labelled **selected
values** of `Event start time zone` and `Event end time zone`, never by searching
its option text or autogenerated IDs. Different start/end zones or display
names without a provable IANA value stop the operation before Save.
Two exact, geographically explicit selected labels observed in the live picker
are also recognized: `Lagos, Nigeria West Africa Time - Lagos (GMT+01:00)` maps
to `Africa/Lagos`; `Nairobi, Kenya East Africa Time (GMT+03:00)` maps to
`Africa/Nairobi`. The selected control value (or native select's single selected
option) must prove the zone at **both** endpoints. Matching an unselected Lagos
option cannot override a selected Nairobi end zone. Offsets alone and other
unrecognized display labels remain insufficient; the device zone is never
used as evidence of the event's configured zone.

Existing editors/dialogs, all-day events, recurring events, missing edit
permissions, changed captured titles/times, unsupported markup, unverifiable
zones and user interference stop the operation. Staged forms are left visible
for inspection, never silently discarded. No second Save is attempted.

A result is `saved` only after a fresh Google "Event saved" confirmation **and**
reopening the exact event and reading back the reviewed date, times, title and
zone. That verification editor remains open without additional changes.
If the event moves outside the loaded view, or Save's acknowledgment/readback is
missing, the result is `uncertain`: inspect Calendar before reviewing another
move. A successful click alone is never reported as a successful reschedule.

## Main-process integration

`BrowserBridge.moveCalendarEvent(move, beforeWrite)` accepts the immutable
`BrowserCalendarMove` contract from `src/shared/browser-calendar.ts`. The caller
must bind it to the exact stored, user-confirmed preview, archived item/provider
identity, revision, account/source selection and AI permission.

`beforeWrite` is a synchronous, repeatable validation callback, invoked when
queuing, when leasing, and immediately before granting Save authorization. It
must **not** consume the approval on its first invocation. It should throw if
any permission, account, revision or approval has changed. Responses have only
bounded enumerated codes and fixed main-process messages, never raw page text.

The authenticated loopback bridge adds protocol-1 POST endpoints:

- `/calendar/poll`: selected Calendar registration, tab ID and document ID;
  returns at most one memory-only job with a random request ID and lease.
- `/calendar/authorize`: same lease/client/tab/document/account route binding;
  repeat validation, then a one-use Save authorization valid for at most 1.5s.
- `/calendar/complete`: same binding plus an allowlisted result code.

Tokens remain in the extension worker's trusted storage. Content scripts never
receive them. The worker validates the browser's actual top-frame sender and
current tab URL before dispatch/authorization/completion. No externally
connectable or arbitrary-command bridge is added.

Only one move may be pending. A move expires after at most 90 seconds (or its
preview deadline, if earlier). Disconnect, lock/stop, pairing revocation, page
replacement, worker loss and expired jobs cannot create replayable work.
Missing acknowledgment after Save authorization is conservatively uncertain.
Restarting either side never requeues an action.

### Readiness without a write

After an authenticated protocol-1 poll, `BrowserStatus.clients` exposes
`calendarActions: { protocol: 1, lastSeenAt, ready }` for that paired companion.
`ready` means a Calendar page has polled within the last 30 seconds and the
bridge is running. Reload the updated extension and a selected, visible
Calendar tab, then inspect this status—no proposal or event write is needed.
The observation is memory-only and cleared on stop/revocation. It confirms
companion protocol availability, **not** AI consent, permission to modify a
particular event, or successful recognition of that event's editor/time zone.

## Validation

`tests/browser-calendar-actions.test.ts` exercises isolated loopback leases and
real Chromium/Edge DOM fixtures, including English/French successful readback,
wrong account/event, stale capture, recurring/all-day events, missing zone,
denied Save authorization, guest-confirmation dialogs and mismatched readback.
Fixtures do not contact Google or write to a real calendar. They establish the
supported DOM contract, **not universal compatibility with every live Google
Calendar rollout**. Unsupported live markup fails closed with browser guidance.
